# AI Team — автономная дискуссия команды по BLD System

Команда из 4 AI-агентов (CTO, Senior Backend, Product/Frontend,
QA/Security) сама смотрит git log твоих репозиториев, находит спорный
коммит/изменение и устраивает дискуссию — без жёсткого ведущего,
с реальным доступом к коду через tools.

## Структура

```
ai-team/
├── config/
│   ├── models.py          # какая модель на какой роли
│   └── client_factory.py  # подключение к Azure AI Foundry
├── agents/
│   └── team.py             # личности агентов (промпты)
├── tools/
│   └── repo_tools.py       # git clone/log/diff/grep/read для агентов
├── workflows/
│   └── discussion.py       # сборка GroupChat + topic scout
├── main.py
├── requirements.txt
└── .env.example
```

## Установка

```bash
cd ai-team
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Настройка

1. Скопируй `.env.example` в `.env`:
   ```bash
   cp .env.example .env
   ```

2. Заполни `FOUNDRY_PROJECT_ENDPOINT` — это project endpoint твоего
   проекта в Azure AI Foundry (НЕ resource endpoint). Найти его:
   Azure AI Foundry portal → твой проект → Overview → "Project endpoint".

3. Авторизуйся в Azure (один раз, локально):
   ```bash
   az login
   ```
   Это даёт `DefaultAzureCredential` доступ без хранения ключей в коде.

4. Создай GitHub Personal Access Token (classic, scope `repo`) и впиши
   в `GITHUB_TOKEN` в `.env`. Нужен, т.к. репозитории приватные.

5. **Проверь имена deployment'ов в `config/models.py`.** Значения там
   (`o3`, `gpt-5.1`, `gpt-5.4-mini`, `gpt-5.3-codex` и т.д.) — это
   ПРЕДПОЛОЖЕНИЕ, что твои deployment'ы в Azure AI Foundry называются
   так же, как сами модели. На практике у тебя могут быть другие
   названия деплоев (например `gpt51-team-deploy`). Зайди в Foundry →
   Deployments и сверь точные имена — поправь `config/models.py` или
   задай через `.env` (`MODEL_CTO=...` и т.д.), не трогая код.

## Запуск

```bash
python main.py
```

Что произойдёт:
1. Клонируются (или обновляются) `bld-system` и `bld-panel` в `./repos`.
2. "Code Scout" (модель на codex) смотрит последние коммиты обоих репо
   и формулирует один конкретный спорный вопрос.
3. Запускается дискуссия — сообщения агентов печатаются в реальном
   времени по мере поступления.
4. Дискуссия останавливается либо по решению модератора ("пришли
   к выводу"), либо по достижении лимита в 24 сообщения (защита
   от бесконечного спора и расхода кредитов — задаётся в
   `workflows/discussion.py`, переменная `MAX_MESSAGES`).

## Что точно нужно подкрутить под себя

- **Лимит сообщений** (`MAX_MESSAGES` в `workflows/discussion.py`) —
  начни с малого (10-12), посмотри как идёт спор, потом увеличивай.
- **Личности агентов** (`agents/team.py`) — это самое важное место.
  Если дискуссия будет слишком вежливой — усиливай в промптах
  конкретные триггеры несогласия между ролями.
- **Имена deployment'ов** (см. п.5 выше) — без этого вообще не
  запустится, framework должен достучаться до реально существующих
  деплоев в твоём Foundry-проекте.
- **Расходы**: каждый агент с tools может делать несколько вызовов
  read_file/grep_repo за один свой "ход" — это быстро накручивает
  токены при топовых reasoning-моделях. Если кредиты важны —
  начинай с дешёвых моделей по всем ролям, потом подними CTO/QA
  на топовые, когда логика дискуссии тебя устроит.

## Логичный следующий шаг

Сейчас итог дискуссии просто печатается в консоль и теряется.
Когда логика дискуссии тебя устроит — следующим шагом стоит добавить
сохранение итога (например, в файл `decisions/<дата>.md` или как
GitHub Issue в репозиторий через `gh` CLI / GitHub API) — чтобы споры
команды превращались в трекаемые решения, а не разговор в пустоту.
Могу написать это сразу следующим шагом, если зайдёт.
